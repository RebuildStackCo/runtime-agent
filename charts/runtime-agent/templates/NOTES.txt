The agent collects into its local spool and ships nothing: backend transport is
not built yet. Read charts/runtime-agent/values.yaml for what you can change,
and docs/security.md for what the agent can reach.

Every pod answers health probes on port {{ include "runtime-agent.healthPort" . }} at /livez and /readyz, in every
profile (ADR 0069). Readiness means the caches are synced, so the rollout below
returns when the agent is actually collecting rather than when it has started:

  kubectl -n {{ .Release.Namespace }} rollout status deployment/{{ include "runtime-agent.controllerName" . }}

CHECK ONE THING: the NetworkPolicy needs a CNI that enforces it.

This release created a NetworkPolicy restricting the controller's node-report
receiver to the node DaemonSet. Kubernetes accepts that object on every cluster,
including clusters whose CNI ignores it — there is no error and no warning, so
an unenforced policy looks exactly like an enforced one.

Verify it rather than assume it. Calico, Cilium, Antrea and GKE Dataplane V2
enforce policies; EKS does so only with the VPC CNI's network-policy agent
enabled, and kind's default CNI does not enforce them at all.

  kubectl -n {{ .Release.Namespace }} get networkpolicy {{ include "runtime-agent.controllerName" . }}

What this changes if it is not enforced: the receiver on port 8080 is reachable
by any pod in the cluster. What it does not change: what a caller may say. Every
request is authenticated by audience, signature against your cluster's JWKS, a
pinned ServiceAccount subject, and the node named in the caller's own token, and
none of those depend on your CNI (ADR 0040).

The policy has a second rule, on port {{ include "runtime-agent.healthPort" . }}, with no source restriction: the
probes come from your kubelet at the node's address, which no pod selector can
name. What it admits is two read-only paths that answer about the agent and name
nothing in your cluster (ADR 0069).
{{- end }}
{{- if and (include "runtime-agent.nodeEnabled" .) .Values.profiling.pprof.enabled }}

READ THIS ONE: the agent will connect to your workloads.

Every other access this agent has is a read of the API server or of /proc. This
one is not. For each collected workload whose binary links net/http/pprof, the
controller fetches the /debug/pprof/ index page once per image and port, from a
pod's own address. No other path is ever requested.
{{- if .Values.profiling.pprof.pull }}

Where that page answers, the controller then fetches a ten-second CPU profile,
which runs your process's own profiler for those ten seconds. It is the one
thing this agent does that your workload can notice. What it costs is bounded by
construction, not by a setting: one capture at a time and at most ten per
five-minute round, so a hundred seconds of profiling per five minutes across the
whole cluster. A workload that refuses — because its own continuous profiler
holds the single slot Go allows — is left alone for six hours, not competed with.

Every attempt appears in the controller's log, one line each, naming the
workload and what came of it:

  kubectl -n {{ .Release.Namespace }} logs deployment/{{ include "runtime-agent.controllerName" . }} | grep 'pprof profile pull'
{{- end }}

To switch it off entirely, set profiling.pprof.enabled=false.
{{- if .Values.profiling.pprof.pull }}
To keep the discovery and drop only the captures, set profiling.pprof.pull=false.
{{- end }}

To exclude one workload while keeping everything else collected about it,
annotate the object itself — never its pod template, which would roll every
replica:

  kubectl -n YOUR_NAMESPACE annotate deployment/YOUR_WORKLOAD rebuildstack.co/profile=false

The same annotation works on a Namespace and on a Pod, and
rebuildstack.co/collect=false still excludes both profiling and everything else.
Section 10.3 of docs/security.md states the whole of it.
{{- end }}

This profile installs the node DaemonSet, which runs as root with hostPID and
CAP_SYS_PTRACE. That is a decision to trust this image with each node it runs
on. docs/security.md section 7.1 states exactly what the privilege permits —
read it before rolling this out widely, and note that the default tolerations
put the DaemonSet on control-plane nodes too.
